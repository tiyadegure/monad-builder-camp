## 2. 你获得了什么反馈？

### 刘力铭（Risk & Product）
- **他们现在怎么解决？**  
  现在主要是协议原生 keeper + 通用 bot（如 Euler liquidation bot-v3），用户自己看 Telegram 监控或浏览器查健康因子。
- **他们最在意什么？**  
  不是“能不能清算”，而是“能不能提前知道会不会爆仓、应该补多少、什么时候补”。他特别提到：如果真有产品商业化，宣传“0 清仓率”可能是卖点。
- **最意外的一条反馈是什么？**  
  他看了一眼 Git 就说“P0/P1 都完成了”，然后直接在现有预警基础上提出要加“金融风控层”，不是从零重新设计，而是在已有架构上补一层用户侧风险叙事。

### Eflier（Dev 自检）
- **他们现在怎么解决？**  
  靠代码硬跑：直接读 Aave/Euler 链上数据，手动算 HF，手动拼 calldata。
- **他们最在意什么？**  
  接口是否稳定、selector 是否经过主网验证、模拟是否零 warning。他关心“能不能在 Hackathon 现场一次跑通”，而不是代码是否优雅。
- **最意外的一条反馈是什么？**  
  原本以为“多协议”是最难的部分，结果发现真正缺的是“用户侧为什么要在乎这个数字”——技术跑通了，产品叙事反而更关键。

### TiyaDegurechaff（Researcher 自检）
- **他们现在怎么解决？**  
  看 DefiLlama / 浏览器 / 协议文档，靠经验判断“这个协议能不能做”。
- **他们最在意什么？**  
  数据是否新、竞品是否真的存在、方向是否有人用过。她关心“这个方向是不是真空白，还是只是我们不知道的竞品”。
- **最意外的一条反馈是什么？**  
  刘力铭提到“0 清仓率”可以作为商业卖点，这比“更快的清算机器人”更有用户感知；原本以为 Keeper 是核心用户，没想到普通借款人也可能是付费用户。

## 3. 团队下一步决定

**决定：继续 + 缩小范围 + 调整方向**

### 继续
- `monad-liq-mvp` 核心方向不动：多协议健康因子监控 + 清算交易草稿
- Week 4 Demo 仍以“监控 → 识别 → 草稿”为 happy path

### 缩小范围
- Week 4 不追求接满 4 个协议，只做 Aave + Euler 双协议
- AI 功能不接外部 LLM，先用规则模板生成风险解释（Issue #10）
- 不做 CLOB 实盘下单、不做 MEV、不做前端钱包

### 调整方向
- 架构从“单线清算 bot”调整为“双轨”：
  - **Liquidator 轨**：给 Keeper / Operator 看可清算仓位 + 交易草稿 + 利润估算
  - **User 轨**：给借款人看 Risk Rating / Stress Test / AI Explanation / Deleverage 建议
- 把 Issue #8-#14 的优先级重新排序：User 轨的 Risk Rating + Stress Test + AI Explanation 提到 P0，和 Liquidator 轨并行

### 原因
- 刘力铭的反馈让团队意识到：这个项目的用户不只是 Keeper，普通借款人更需要“提前知道会不会爆仓”。
- 现有代码已经覆盖 Liquidator 轨的基础，User 轨可以在其上加一层解释和建议，不需要从零写。
- 这样 Demo 可以同时打动两类用户，评委看到的不是一个“清算 bot”，而是一个“链上风险管家”。
