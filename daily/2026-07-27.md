## 2. Week 4 交付形式评估

纯 CLI 原型在 Hackathon 演示里的短板很明显：评委需要看到“用户怎么用”，而不是“开发者怎么跑”。但加前端/Web UI 又需要额外时间，且容易偏离 Dev 强项。

三个候选形态的详细对比：

### 形态 A：CLI 直接交付

```
node stake-agent.mjs 1
```

- 优势：已经跑通，零额外工作。适合“开发者对开发者”的评审。
- 风险：非技术评委无法直观理解“这为什么是 Agent 能力”。评委需要自己 clone repo、装依赖、跑命令，摩擦成本极高。
- 24h 可行性：100%
- 适合场景：纯技术赛道、评委都是开发者

### 形态 B：MCP server 包一层

```
用户 / Agent 输入："Stake 1 MON into aPriori"
→ MCP tool 解析 intent（verb=stake, amount=1, protocol=apriori）
→ Moss framework discover → load → action 构建 deposit tx
→ 返回 tx 草稿 + convertToShares 估算的 aprMON 数量
```

- 优势：最符合“AI Agent + Moss”叙事。评委一看就知道“这个 Agent 能理解自然语言并生成链上交易”。MCP 是 Model Context Protocol 的标准接口，Claude/Cursor/其他 LLM 都能直接调用。
- 风险：需要写 MCP tool wrapper + 演示环境（比如用 Claude Desktop 或 Cursor 现场演示）。MCP server 本身不难写，难的是演示时网络/环境不出问题。
- 24h 可行性：70%（假设今天能搭起 stdio transport + 一个 tool）
- 适合场景：AI + Web3 赛道、评委关心“Agent 能力”而不仅是“链上交互”

### 形态 C：简单 Express Web UI

```
用户打开网页 → 输入金额 → 点击 Stake → 看到 tx 草稿
```

- 优势：最直观，非技术评委也能理解。网页 Everyone 都能打开。
- 风险：需要写前端 + 签名流程。但 Moss 的设计是“只模拟不签名”，这意味着按钮点了之后不会真的广播 tx，需要解释“为什么按钮点了不广播”。这个解释在 2 分钟 Demo 里很浪费时间。
- 24h 可行性：50%（HTML + Express 简单，但签名/广播的 mock 逻辑要写清楚）
- 适合场景：产品/设计赛道、评委看重 UI/UX

**决定：走 MCP server 路线（形态 B）。**

理由细化为五点：

1. **叙事对齐**：Week 3 Dev README 里已经写了“接自然语言输入”的目标，MCP 是最短路径，不需要解释“为什么不广播”。
2. **生态对齐**：Moss 生态本身在做 MCP 标准化（`@themoss/system` 里已有 MCP transport 概念），和 PR #104 的主题一致。
3. **证据复用**：adapter 层已经写好，MCP wrapper 只是加一层 intent parsing + tool definition，不需要重写业务逻辑。
4. **评委友好**：AI Agent 是当前最热的叙事，MCP 是标准接口，评委一听就懂“这是什么”。
5. **风险可控**：CLI 原型已经跑通，MCP wrapper 失败 worst case 是回退到 CLI 演示，不会白做工。

## 3. Week 4 Day 1 最小 MVP

今天的目标是把 MCP server 搭起来，能跑通一个 happy path。先定义清楚“跑通”的标准：

**Happy Path：**

```
用户 / 评委输入："Stake 1 MON into aPriori"
→ MCP tool `apriori_stake` 被调用
→ intent parser 提取 { verb: "stake", amount: 1, protocol: "apriori" }
→ Moss framework discover("apriori") → load() → action("stake")
→ action 层调用 adapter.ts stake() 构建 deposit tx
→ 返回：
  - tx.to: 0x0c65a...0852 (aprMON proxy)
  - tx.value: 1 ETH (1 MON)
  - tx.data: 0x6e553f65... (deposit selector + encoded args)
  - receipt.estimatedShares: 0.9985 aprMON (convertToShares 视图返回)
```

**不追求（明确排除）：**

- 钱包签名：Moss 设计只模拟不签名，tx 草稿交用户钱包。MCP server 也不签名。
- 完整 error handling：先跑通 happy path，revert / insufficient balance / slippage 等错误后天再加。
- 多协议切换：先只接 aPriori，其他 adapter 后面再挂。
- 持久化 / 会话管理：stateless MCP tool，每次调用独立。

**文件结构（脑图，不一定全写）：**

## 4. 关键认知

- **Hackathon 交付形式先于功能开发。** 如果先花 6 小时写前端，最后发现评委最在意“Agent 能不能理解自然语言”，就本末倒置了。今天花 30 分钟评估形态，比明天返工强。
- **MCP server 是最小叙事单元。** 它把“CLI 能做什么”翻译成“AI 能调用什么”，评委一听就懂。不需要解释技术细节，只需要演示“输入自然语言 → 得到可执行交易”。
- **PR #104 在 Hackathon 材料里是“证据”，不是“产品”。** 证据链：adapter 已提交 → 单测通过 → 主网 e2e → selector 已验证 → review 修订版已推送。产品是 Week 4 的 MCP wrapper。不要把时间花在“再改一遍 adapter”上。
- **Solo Hackathon 的核心矛盾是“叙事完整度 vs 实现深度”。** 有队友时可以分工（Research 写故事、Ops 做演示、Dev 写代码），单人时必须选一个最会讲的角度。我选“AI Agent + 可验证链上交互”，因为 adapter 代码本身就是最硬的证据。
- **Decision Log 在 Week 4 变成“为什么选 MCP 而不是前端”。** Day 1 的记录在最后一天评审时能救命：评委问“为什么不做成网页”，你能拿出今天的评估表，说明是主动选择，不是做不到。
